FIN-01 [P0] Edit Bill updates the sale header but never the line items
--------------------------------------------------------------------------------
Where:  supabase_schema.sql:1087-1280  edit_sale_transaction
        src/hooks/useSales.js:165-235   updateSale

The problem:
  Orders are created as a header row in `sales` PLUS one row per allocation in
  `sale_items` — place_pooled_order_transaction writes up to four
  (paid_manufactured, paid_resell, free_manufactured, free_resell) at
  supabase_schema.sql:2349-2366.

  edit_sale_transaction never touches `sale_items`. It updates only the
  `sales` header (step 5, line 1226-1234). After an edit the two disagree
  permanently, and different screens read different ones:

    reads sale_items (stale, pre-edit)   |  reads sales.quantity (new)
    -------------------------------------|------------------------------
    Bill PDF        useSales.js:109      |  Daily Report  useDailyReport.js:280
    Public bill     schema:2482-2492     |  Sales History SalesPage table
    Dashboard cubes useDashboard.js:92   |  Customer Profile totals
    Stock restore   useSales.js:242-245  |

  Concrete consequence: correct a sale from 100 cubes to 50. The customer's
  bill link and the PDF still say 100. The dashboard still counts 100 cubes
  sold. Then delete that sale with "restore stock" and 100 cubes are returned
  to inventory for a sale of 50 — 50 cubes created from nothing.

Fix:
  Rewrite edit_sale_transaction to delete and re-insert `sale_items` for the
  sale as part of the same transaction, mirroring the four-line structure
  place_pooled_order_transaction produces. Restore stock from the OLD
  sale_items rows (not from sales.quantity), then deduct against the new ones.
  Add a check constraint or a test asserting
  sum(sale_items.quantity where not is_free) = sales.quantity.

FIN-02 [P0] Debt created_at is overwritten — aging and FIFO both break
--------------------------------------------------------------------------------
Where:  supabase_schema.sql:2317   inside place_pooled_order_transaction
          created_at = case when v_old_new_remaining > 0 then v_now
                            else created_at end
Read by: src/pages/DebtsPage.jsx:303 (aging buckets), :338 (aging filter)
        supabase_schema.sql:2301 (the FIFO `order by created_at asc`)

The problem:
  Whenever a cash order auto-applies against an older debt and leaves a
  balance, that debt's created_at is reset to now.
   - A 6-month-old debt jumps from the "90+ days" bucket into "0-30 days".
     Every collections decision made from the Debt Aging card is wrong.
   - FIFO inverts: the partially-paid OLD debt becomes the NEWEST, so the next
     cash order pays down a genuinely newer debt ahead of it. The oldest debt
     can be starved indefinitely.
   - The original incurrence date is gone. No other column holds it.

Fix:
  1. Delete the created_at mutation from the UPDATE at :2311-2318.
  2. If "last activity" is wanted on screen, add a separate column:
       alter table public.debts add column last_activity_at timestamptz;
     and set that instead.
  3. Repair the existing damage — a debt's true date is its sale's date:
       update public.debts d
          set created_at = s.sale_date
         from public.sales s
        where s.id = d.sale_id and d.created_at <> s.sale_date;
     Run this in a transaction and check the row count first.

FIN-03 [P0] Deleting a sale leaves the debt reductions it paid for in place
--------------------------------------------------------------------------------
Where:  src/hooks/useSales.js:237-289   deleteSale
        supabase_schema.sql:2293-2330   the FIFO offset that created them

The problem:
  A cash order automatically pays down the customer's older debts, writing
  is_auto_applied rows into debt_settlements against OTHER debts.

  deleteSale removes the sale. The FK cascade removes that sale's own debt and
  its sale_items. It does NOT touch the other debts that were reduced, and it
  does NOT remove the is_auto_applied settlement rows.

  Net result: the revenue vanishes, the debt reduction it paid for stays.
  Customers show as having paid debts that nothing paid for. Repeat this a few
  times and the receivables ledger is quietly understated with no trace.

Second defect in the same function:
  Stock restore (lines 249-276) is an unlocked read-then-write per cube type —
  two concurrent deletes both read the same starting quantity and one
  overwrites the other. It also writes no inventory_transactions row, so the
  stock movement is invisible in Inventory History. And it runs BEFORE
  soft_delete_row (line 281): if the delete then fails, stock has already been
  inflated with no record of why.

Fix:
  One RPC — delete_sale_transaction(p_sale_id, p_restore_stock) — that in a
  single transaction:
    - locks inventory, restores per sale_items line, writes an 'adjustment'
      inventory_transactions row referencing the sale_code
    - selects this sale's is_auto_applied settlements, adds each amount back to
      its target debt's remaining_amount, recomputes status, deletes the rows
    - snapshots all of it into `trash` (extend soft_delete_row's children so a
      restore is symmetric)
    - deletes the sale
  In the UI, when a sale has auto-applied settlements, show the operator
  exactly which debts will be un-paid before they confirm.

FIN-04 [P0] Multi-debt settlement is not atomic
--------------------------------------------------------------------------------
Where:  src/hooks/useDebts.js:186-317, the loop at :221-246

The problem:
  A payment spanning several debts calls settle_debt_transaction once per debt
  in a JavaScript for-loop. Each call commits independently.

  If call #3 fails — network drop, timeout, RLS — the function throws. Calls #1
  and #2 are already committed. The operator sees "Failed to settle debt",
  assumes nothing happened, and retries. The first two debts are now paid
  twice. There is no compensating rollback anywhere in the file.

  Two further defects in the same function:
   - Line 267 reads `lastSettlement.id` with no null guard. If the loop body
     never executes (every outstanding debt has remaining_amount = 0 but status
     != 'settled'), this throws a TypeError after the money work is done.
   - The bank_deposits / cheque_records insert (:269-296) is a THIRD separate
     transaction. It fails into a `ledgerWarning` toast — honest, but the books
     stay out of balance until a human notices and acts on a toast.

Fix:
  One RPC, settle_customer_debt_transaction(p_customer_id, p_amount,
  p_method, p_details, p_created_by), doing all of it in one transaction:
    - lock the customer's unsettled debts: order by created_at for update
    - validate p_amount <= sum(remaining_amount)
    - apply FIFO, one debt_settlements row per debt touched
    - for bank_transfer insert bank_deposits; for cheque insert cheque_records
    - return the combined receipt JSON, including the customer's new total
      outstanding (which also fixes FIN-14)
  The JS then becomes a single call, and any failure rolls everything back.

FIN-05 [P0] Cash Balance never subtracts expenses
--------------------------------------------------------------------------------
Where:  src/utils/cashBankMath.js:86

      cashBalance = openingCash + cashSalesTotal + settlementCashTotal
                    + cashReceivesTotal - cashDepositedTotal

The problem:
  Nothing subtracts expenses. The whole Expenses module
  (expense_ledger_rows x expense_amounts, src/hooks/useExpenses.js) is a
  parallel ledger that never touches Cash Balance.

  Every rupee spent out of the cash box still shows as sitting in the till.
  Over a month this drifts by the entire operating expense total, and the
  physical cash count will never reconcile with the screen.

  Confirmed by grep: `totalExpensesAmount` (useDailyReport.js:437) and
  `totalIncome` (:364) are rendered as two independent figures
  (DailyManagerReportView.jsx:320 and :441) and are never netted against each
  other anywhere in the system. There is no net-position, net-cash or profit
  figure in the application at all.

Fix:
  1. Decide the model explicitly — are expenses paid from the till, from the
     bank, or either? Almost certainly "either", which means:
       alter table public.expense_ledger_rows
         add column payment_source text not null default 'cash'
         check (payment_source in ('cash','bank'));
  2. Add a `cashExpenses` / `bankExpenses` input to computeCashBankBalances and
     subtract each from the right balance.
  3. Pass it from BOTH call sites (useCashBank.js:100, useDailyReport.js:445).
  4. Add a "Net Position" line to the Daily Report so income and expenses are
     visibly reconciled rather than sitting side by side.

FIN-07 [P1] Edit Bill ignores the customer's negotiated price
--------------------------------------------------------------------------------
Where:  supabase_schema.sql:1209-1216   edit_sale_transaction step 4

      select price_per_cube into v_inventory_price
        from public.inventory where id = v_new_item_id;
      if public.is_admin() and p_price_per_cube ... then v_final_price := ...

The problem:
  place_pooled_order_transaction resolves the rate as: explicit price, else

                                v_inventory_price);
  Better still, extract it into one shared resolve_cube_price() function so the
  two paths cannot diverge again.

FIN-09 [P1] Edit Bill ignores free cubes entirely
--------------------------------------------------------------------------------
Where:  supabase_schema.sql:1087-1280 (no reference to free_quantity anywhere)
        src/pages/SalesPage.jsx:483-489 (edit form has no free-cubes field)

The problem:
  A sale carries `sales.free_quantity` plus is_free rows in sale_items. The
  edit path has no concept of either.
   - v_old_quantity (line 1131) is sales.quantity — the BILLED count only. The
     free cubes that physically left stock are never restored.
   - The is_free sale_items rows are left behind, still pointing at the sale.
   - sales.free_quantity keeps its old value while everything around it changes.

  Editing a sale that had 20 free cubes leaks those 20 cubes out of inventory
  permanently — they are deducted at order time and never restored.

Fix:
  Add p_free_quantity to edit_sale_transaction's signature, restore
  old_quantity + old_free_quantity, deduct the new pair, and rewrite the
  is_free sale_items rows alongside the paid ones (see FIN-01). Add the field
  to the edit modal in SalesPage.

FIN-10 [P1] Edit Bill never reverses the cash-to-old-debt offset
--------------------------------------------------------------------------------
Where:  supabase_schema.sql:1082-1085 (the comment acknowledging this)

The problem:
  The comment says: "unlike place_order_transaction, this does NOT replay the
  cash-to-old-debt FIFO offset — that offset already happened (or didn't) at
  the time the sale was originally placed."

  That reasoning holds only if the total is unchanged. Edit a cash sale from
  LKR 10,000 down to LKR 1,000 and 10,000 remains applied against the
  customer's old debts, funded by a sale that is now worth 1,000. Nine
  thousand rupees of debt was written off against money that no longer exists.

  Same gap on debt -> cash conversion (lines 1259-1265): the debt is deleted,
  but the new cash never gets applied to older debts the way a fresh cash order
  would. Two identical end states, two different ledger outcomes.

Fix:
  On any change to total_amount or payment_type, reverse this sale's
  is_auto_applied settlements first (same reversal logic as FIN-03), then
  re-run the FIFO offset against the new total. Extract the FIFO loop from
  place_pooled_order_transaction (:2296-2330) into a shared
  apply_cash_to_old_debts(p_customer_id, p_amount, p_sale_code, p_created_by)
  function and call it from both places.

FIN-13 [P1] Daily Report stock figures are wrong for every past date
--------------------------------------------------------------------------------
Where:  src/hooks/useDailyReport.js:319-326

      previousDayBalance = currentTotalStock - todaysProduction
                           - todaysPurchase + todaysSalesQty + freeIssue
      closingBalance = previousDayBalance + todaysProduction
                       + todaysPurchase - freeIssue - todaysSalesQty

The problem:
  currentTotalStock is LIVE inventory (line 318). The formula only backs out
  movements inside the selected window — movements AFTER the window are never
  backed out.

  Open the report for last Tuesday and the opening balance is computed from
  today's stock. It is wrong by the sum of every movement since. And the
  closing figure is algebraically forced straight back to the live total
  (substitute and the terms cancel), so closingBalance always equals today's
  stock no matter which date is selected.

  A signed-off report for a past day therefore states a closing stock figure
  that changes every time it is reopened.

Fix:
  Derive from the transaction ledger, not from live quantity.
  inventory_transactions already stores new_quantity per row, so:
      opening = new_quantity of the last transaction before window_start,
                per cube type (0 if none)
      closing = opening + movements within the window
  Add the supporting index:
      create index on public.inventory_transactions (inventory_id, created_at);

FIN-16 [P2] Client-side balance checks race the server
--------------------------------------------------------------------------------
Where:  src/hooks/useCashBank.js:271-278 (deposit vs cashBalance / handCheques)
        :366-369 (withdrawal vs bankBalancesByName)
        :330-352 depositChequeRecord — two writes, no transaction
        :288-307 deleteBankDeposit — two writes, no transaction

The problem:
  Each of these validates against a client-side snapshot that may be hundreds
  of milliseconds stale, then writes with a plain insert that has no
  server-side equivalent check. Two operators can both pass and both write.

  The two-write pairs are worse than a stale check:
   - depositChequeRecord inserts bank_deposits, THEN marks the cheque
     'deposited'. If the second call fails the money is in Bank Balance AND
     still counted in Hand Cheques — created from nothing.
   - deleteBankDeposit reverts the cheque to 'pending' FIRST, then deletes the
     deposit. If the delete fails, same double-count in reverse.

  (transport_trips is the one place this is done right — a partial unique index
  backs the pre-check and the code handles 23505 at useTransportTrips.js:87.
  Use it as the template.)

Fix:
  One RPC per pair — deposit_cheque_transaction, delete_bank_deposit_transaction
  — doing both statements in one transaction, recomputing the balance under
  lock. Keep the client-side checks for fast feedback, but stop treating them
  as the guarantee.

--------------------------------------------------------------------------------
Where:  src/pages/SalesPage.jsx:483-489 (handleEditClick)
        src/hooks/useSales.js:174-176 (validation)

BRK-02 [P0] Retrying a failed Expense save creates duplicate ledger rows
--------------------------------------------------------------------------------
Where:  src/components/ExpenseCashBookGrid.jsx:118-139 (handleSaveChanges)
        src/hooks/useExpenses.js:190-226 (saveLedgerRow)

The problem:
  saveLedgerRow inserts the ledger row first (:196-203), then upserts each cell
  amount in a sequential loop (:212-221), throwing on the first cell failure.

  handleSaveChanges loops over edited rows awaiting each one, and only clears
  editingIds on full success (line 133). The returned real `rowId` is
  discarded. The resync effect (:59-68) is gated on `editingIds.size === 0`, so
  on failure localRows keeps the `temp-...` id.

  Sequence: new row -> ledger row INSERTED -> a cell upsert fails -> toast
  "Failed to save changes" -> row still shows as editing with its temp id ->
  operator clicks Save again -> `isNew` is still true (useExpenses.js:194) ->
  a SECOND ledger row is inserted.

  Every retry adds another duplicate expense row, each carrying whichever cells
  did land. The Cash Book grand total (useExpenses.js:271) counts them all.

Fix:
  1. In handleSaveChanges, capture the returned rowId and immediately update
     that entry in localRows so a retry takes the UPDATE branch.
  2. Clear the successfully-saved ids from editingIds even on partial failure,
     and report which rows failed.
  3. Make saveLedgerRow atomic — batch the cells into one
     `.upsert([...])` array call instead of a loop, or move the whole row save
     into an RPC. That removes the partial-save window entirely.

BRK-04 [P1] Global search only searches an arbitrary 100 rows per table
--------------------------------------------------------------------------------
Where:  src/components/GlobalSearchModal.jsx:49-57

The problem:
  Every query is `.limit(100)` with NO order by, and the filtering happens
  afterwards client-side in a useMemo. Which 100 rows Postgres returns is
